## 二、两章内容的整体理解

### 2.1 第10章：给客户机准备一台“能运行的计算机”

我把虚拟机理解为：在真实硬件之上，为客户操作系统提供一套可以使用的 CPU、内存和设备环境。客户机可以拥有自己的内核，但它使用的资源仍然需要由宿主系统管理。

教材按照 CPU、内存和 I/O 三个方面展开，这样读比一开始记住很多软件名称更清楚。

- **CPU 虚拟化**解决客户机指令怎样执行、哪些事件需要交给虚拟机监控器处理的问题。KVM 利用处理器的硬件辅助虚拟化能力；典型 QEMU-KVM 中，vCPU 由宿主线程承载，并由 Linux 调度器安排运行。
- **内存虚拟化**需要把客户机虚拟地址转换为客户机物理地址，再对应到宿主机物理地址。客户机所理解的“物理内存”，仍然处在更外层的资源管理之下。
- **I/O 虚拟化**为客户机提供可以使用的设备接口。设备模拟、virtio 和设备直通采用不同路径，在兼容性、性能和隔离要求之间各有取舍。

在典型分工中，QEMU 在用户空间组织虚拟机和设备模型，KVM 提供内核中的虚拟化能力，二者通过 `/dev/kvm` 等接口配合。实际 I/O 也可能采用卸载或直通方式，不能把所有路径都理解为完整的软件设备模拟。

第10章后半部分还介绍了 StratoVirt。它同样基于 KVM，通过组件化设计支持轻量虚拟机和标准虚拟机，并介绍了 Rust 构建、客户机内核与根文件系统准备、设备条件检查等步骤。我从中体会到，**“轻量”来自功能范围和实现方式的取舍，轻量虚拟机仍然需要准备客户机的运行环境。** 教材中的启动时间和内存数字属于特定条件下的示例，不能直接作为本次学习的实测结果。

### 2.2 第11章：让同一内核中的进程各有活动范围

普通 Linux 进程容器共享承载它们的 Linux 内核。容器中的应用仍然是进程，只是它们看到的资源视图、可用权限和资源额度经过了配置。

我用下面这组对应关系整理第11章的内容：

| 层次 | 主要机制或工具 | 我对其作用的理解 |
| --- | --- | --- |
| 文件系统环境 | 根文件系统、`chroot`、Mount namespace | 决定程序访问怎样的目录和挂载视图 |
| 资源视图 | PID、UTS、IPC、Network、User 等 namespace | 决定进程能看到哪些编号、对象和身份 |
| 资源管理 | cgroups | 对任务组进行资源计量、限制和分配 |
| 启动约定 | OCI 镜像规范、运行时规范 | 约定交付内容及运行时如何准备、启动容器 |
| 生命周期管理 | Docker、iSulad 等引擎 | 组织镜像、容器、网络和存储等操作 |

教材先讲 `chroot`，再讲 namespace 和 cgroups，最后进入 OCI、Docker 和 iSula。这条顺序让我看到，一个容器并非由某一个命令单独“变出来”，而是多种内核能力与用户态工具共同组织的结果。

两章放在一起，可以形成一个便于记忆的比较：

| 比较项 | 典型 QEMU-KVM 虚拟机 | 普通 Linux 进程容器 |
| --- | --- | --- |
| 运行环境 | 虚拟硬件及客户操作系统 | 共享内核中的隔离进程环境 |
| 内核 | 客户机有自己的内核 | 应用共享承载它的 Linux 内核 |
| 宿主如何管理 CPU | 调度承载 vCPU 的线程等 | 调度容器中的任务 |
| 主要边界 | 虚拟化执行环境与虚拟资源 | namespace、资源控制与权限等机制 |
| 学习时的重点 | 分清客户机和宿主机两层状态 | 分清资源视图、资源额度和权限范围 |

## 三、学习中遇到的问题与解决方案

### 问题一：以前用 QEMU 调试内核，是否就说明已经使用了 KVM？

**疑问来源：**第10章第10.1、10.3节。此前我用过 QEMU 加载内核，看到“QEMU-KVM”这个名称时，容易把两者直接画上等号。

**向 AI 提问的方式：**“QEMU 与 KVM 各负责什么？只看到 QEMU 成功运行，能否证明启用了硬件虚拟化加速？”

**核对与解决：**QEMU 可以采用 TCG 进行软件仿真，也可以借助 KVM 等加速器。启动成功只能证明当前配置可以运行，不能单独证明使用了 KVM。判断时应检查加速器配置、宿主支持情况和运行状态，而不是根据软件名称推断。

这也解释了跨架构时为什么要格外注意：QEMU 支持的目标体系结构较多，但 KVM 依赖宿主硬件的虚拟化能力，不能把“QEMU 可以仿真另一种 CPU”直接推广成“KVM 也能同样加速”。

**我的收获：**以前使用工具时只关心“能否启动”，现在还要问“它采用了哪一种实现路径”。

### 问题二：执行 chroot 后是不是就拥有了完整容器？文件存在却提示找不到，又该怎么办？

**疑问来源：**第11.2.1节。`chroot` 看起来能把程序“关进另一个目录”，容易让我误认为网络、PID 和权限也一起被隔离了。

**向 AI 提问的方式：**“请分别解释 chroot 改变了什么、没有改变什么；如果新根目录里明明有 /bin/sh，却启动失败，应检查哪些依赖？”

**核对与解决：**教材的源码路径最终涉及 `set_fs_root()`，核心是改变进程的路径根。它不会单独建立独立的 PID、网络和资源限制，也不能独自承担完整的安全隔离。还应注意，它不会自动改变当前工作目录，也不会关闭已有文件描述符。

对于“文件存在却提示找不到”的情形，除了路径本身，还应检查 ELF 解释器、共享库或脚本解释器是否存在于新根目录，以及程序架构是否匹配。可先在外部用 `file`、`readelf -l`、`readelf -d` 检查文件格式与依赖，再沿对应路径补齐 rootfs。

这与前面学习动态链接的内容连了起来：**复制一个可执行文件，并不等于已经复制它的完整运行环境。** 如果采用静态程序简化验证，也要说明这是实验条件的选择，不能把它推广为所有程序都不需要其他运行资源。

### 问题三：namespace 已经隔离了资源，为什么还需要 cgroups？教材里的路径为什么可能对不上？

**疑问来源：**第11.2.2—11.2.9节。最初我把“隔离”理解成一个统一功能，后来才发现“看不见别人”和“不能耗尽资源”是两个问题。

**向 AI 提问的方式：**“如果两个进程互相看不到，为什么它们仍可能争抢 CPU 和内存？再比较 cgroup v1 与 v2 的接口差异。”

**核对与解决：**namespace 主要隔离资源视图；cgroups 主要对任务组进行资源计量和控制。Network namespace 可以隔离网络栈，PID namespace 可以形成不同的进程编号视图，但这些本身不等于已经给进程设置 CPU 时间配额或内存上限。

教材介绍了 v1 和 v2，后续示例使用了较多 v1 风格的挂载与 `tasks` 文件。实际环境若采用 v2，就应按统一层级及其控制器接口理解，例如 `cgroup.procs`、`cpu.max`、`memory.max`。还需检查控制器是否可用、父层级是否启用及当前用户是否有管理权限。

例如，在 v2 中把 `cpu.max` 配置为 `50000 100000`，表示每100000微秒周期最多使用50000微秒的 CPU 时间配额，约相当于0.5个逻辑 CPU 的时间额度。这是配置含义的说明，并非本次测量；它也不等于固定绑定半个物理核心。

**我的收获：**遇到接口不一致时，应先确认版本和挂载方式。把“内核支持某项能力”“控制器已启用”和“当前任务已受到限制”分别检查，才能避免只创建一个目录就宣布隔离完成。

## 四、把教材与前期视频主题联系起来

教学进程列出的两组视频主题都强调系统架构与执行过程。本周阅读让我能够从新的角度回看其中的系统调用、调度和执行现场问题。

### 4.1 虚拟机中有两层需要分清的调度关系

客户机内核负责调度客户机进程，宿主机内核负责调度承载 vCPU 的线程等任务。即使客户机已经选中了一个进程，如果对应 vCPU 线程暂时没有获得宿主 CPU 时间，它也无法继续执行。前几周“可运行不等于正在运行”的认识，在这里又多了一层含义。

分析虚拟机变慢的原因时，我会先区分客户机内部负载与宿主 CPU 竞争，再决定观察哪一层，避免只在客户机里寻找原因。

### 4.2 系统调用、VM Exit 与进程切换不是同一种事件

| 事件 | 主要改变或处理什么 | 不能直接推出什么 |
| --- | --- | --- |
| 客户机应用发起系统调用 | 通常进入客户机内核处理服务 | 不意味着每次都必须退出到宿主 QEMU |
| VM Exit | 从客户执行环境把控制权交回宿主虚拟化处理路径 | 不意味着宿主一定切换到另一个任务 |
| 宿主进程调度 | 选择任务，必要时交接宿主执行上下文 | 不等于客户机内部已经发生一次进程切换 |

视频主题中“保护现场、处理事件、恢复执行”的思路仍然有帮助，但必须先说明这是哪一层的现场。客户机寄存器状态与宿主线程的调度现场不能混为一份。

### 4.3 容器把“同一内核的不同视图”具体化了

普通容器内的程序发起系统调用时，请求仍由承载它的 Linux 内核处理。内核结合任务所属的 namespace、资源组和权限解释请求，因此不同容器中的程序可以看到不同 PID、主机名或网络环境。

这使我对“Linux 系统的一般执行过程”有了更具体的补充：内核既要处理程序请求的操作，也要判断这个请求处在哪个资源视图和权限范围内。容器中的环境差异，最终仍然要落到进程关联的数据结构、内核检查和资源控制上。

## 六、学习总结与后续计划

这一周最大的收获，是我开始按层次解释“虚拟化”：虚拟机让客户操作系统获得一套受管理的硬件运行环境，普通容器则让同一内核中的进程获得不同的资源视图与额度。两者都在组织资源，但边界的位置、管理对象和执行路径不同。

对我帮助最大的学习方式，是把大问题拆成可以核对的小问题。例如，先区分 QEMU 的软件仿真与 KVM 加速，再分析启动路径；先检查 rootfs 中的程序及其依赖，再排查启动失败；先确认 cgroup 版本，再找对应的控制文件。ChatGPT 能帮助我快速列出概念之间的关系，但阅读原页和查阅文档，才能发现解释中缺少的条件。

目前仍需实践验证的内容包括：在具备 KVM 条件的 Linux 环境中运行一个最小客户程序；分别观察 namespace 与 cgroup 限制的效果；按教材准备 OCI bundle；在统一测试条件下比较 QEMU 与 StratoVirt、Docker 与 iSulad。教材中的性能结论让我看到了设计目标，真正比较时仍需记录版本、硬件、配置与测量方法。

我希望下一步能够沿着一个具体应用同时观察宿主与客户机，或者沿着一次容器创建请求追到内核机制。这样，读到的名词就能进一步变成自己能够解释和验证的执行过程。
