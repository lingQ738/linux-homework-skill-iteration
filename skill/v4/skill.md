# Linux Markdown 作业

## 通用写作

- 先读题目、评分要求和提供的源码、日志、截图，确认每个问题需要什么证据。沿题目组织章节，不套用旧作业的目录、实验版本或结论。
- 用中文解释概念，再展示与结论直接相关的命令或代码；行内名称用反引号，代码块标注语言。姓名、学号、课程等信息以本次要求和材料为准。
- 只把实际执行并有记录支撑的步骤写成实验事实；示例、预期结果和推断要明确区分。总结回答题目中的问题，避免重述前文。
- 图片使用可访问的相对路径和能说明内容的图注；正文指出图中可观察的关键位置。交付前检查图片、链接、代码围栏、标题层级及文件名。

## 命令与实验记录

- 命令实践类题目按要求分类，说明命令的用途、前置条件、输入与关键输出。准备步骤要足以让读者理解后续命令；不为每条命令堆放无关的终端输出。
- 编译或运行实验记录影响结果的环境、版本、关键参数、修改过的文件以及重新构建步骤；区分原始代码与自己的修改。不要把某个工具链或机器上的输出当成普遍结果。
- 对删除、覆盖、改权限、改用户或改系统配置的命令，交代操作对象和可能影响，优先在测试目录或虚拟机中演示。
- 出错时记录实际报错、原因判断、采取的处理和复查结果；没有解决就如实注明，不编造成功输出。

## 源码与机制分析

- 选取支持结论的最小代码片段，建立“代码路径或条件 → 状态变化 → 可观察输出 → 解释”的对应关系。复杂过程可用文本图或表格说明，不让截图代替分析。
- 分清事件触发、请求设置、实际执行与恢复的位置。例如实验中的时钟处理函数若只置调度标志，就不能写成它在中断中直接完成了上下文切换；以本次源码为准。
- 分析任务或函数切换时，核对执行位置、栈、保存与恢复的状态；区分首次启动与恢复旧任务。寄存器、偏移和调用约定只在当前架构与代码适用时具体展开。
- 区分教学模型与真实 Linux 的完整实现。日志能证明出现过的切换顺序，不自动证明所有调度路径、长期公平性或未展示的内部步骤；需要更强结论时再补相应源码或运行证据。
